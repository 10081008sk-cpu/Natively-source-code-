1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The app is NOT stuck in a Sherpa reconnect loop. SherpaSTT contains no retry
or reconnect logic at all. What the user sees ("STT reconnecting" indefinitely)
is a STICKY RENDERER STATE that is only cleared by a final transcript event,
combined with a VAD decoder bug that prevents any transcript from ever being
produced.

The decisive defect is in SherpaAutoService.drainSegments():

    segment = vad.front();   // <-- src/main/services/SherpaAutoService.ts:268

sherpa-onnx-node's Vad.front(enableExternalBuffer = true) defaults to true.
On this build, calling it with the default throws:

    Error: External buffers are not allowed

drainSegments() catches that error, logs it, and `break`s BEFORE calling
vad.pop(). The VAD queue therefore never drains, no segment is ever decoded,
no transcript event is ever emitted, and the renderer's one-way STT status
machine never receives the "connected" transition that would clear
"Reconnecting".

Reproduced in a real Electron main process:
  - vad.front()      -> throws "External buffers are not allowed"
  - vad.front(false) -> works, decodes synthesized speech correctly
  - vad.pop() must still be called afterwards to advance the queue.

Two secondary amplifiers make the symptom permanent and opaque:
  a) SherpaAutoService swallows all VAD/decode errors internally, so the
     adapter never emits 'error' and main.ts never sets 'failed'.
  b) main.ts only broadcasts state='connected' from a FINAL transcript
     (electron/main.ts:1333-1345). There is no 'connected' broadcast on
     start / reconfigure / session reset, so any earlier 'reconnecting'
     state is sticky.

Confidence in the primary root cause: 95%.

4. RANKED ROOT CAUSES (CONFIDENCE)
--------------------------------------------------------------------------------
 1. 95%  vad.front() external-buffer incompatibility
         SherpaAutoService.drainSegments() calls vad.front() with the default
         enableExternalBuffer=true; it throws "External buffers are not
         allowed"; the catch breaks before vad.pop(); the queue never drains;
         no segment is decoded; no transcript is ever emitted.
         Evidence: reproduced in Electron; vad.front(false) decodes correctly.

 2. 90%  Sticky one-way STT status in the renderer
         'connected' is broadcast only on a FINAL transcript. Start,
         reconfigure, and session reset never re-broadcast 'connected'.
         Combined with cause #1 (no transcript ever), "Reconnecting" is
         permanent and survives session resets.

 3. 85%  Swallowed service errors hide the failure
         SherpaAutoService catches VAD/decode errors in processChunk,
         drainSegments, decodeSegment, and flush, returning '' instead of
         emitting 'error'. main.ts therefore never sets 'failed', and the UI
         gets no actionable error — only an endless "Reconnecting".

 4. 50%  Effective provider is not Sherpa
         CredentialsManager self-heals 'none' -> 'natively', and saving a
         Natively API key calls setSttProvider('natively'). If so,
         NativelyProSTT's genuine reconnect loop is what the user sees.
         Must be ruled out via getSttProvider() and stt-status.provider.

 5. 30%  Sample-rate flag bug (mic path)
         _micSttRateApplied is set true even when getSampleRate() returns 0;
         setSampleRate ignores non-positive values, leaving the 48 kHz
         default. System path self-heals via sample_rate_changed; mic path
         does not. Would cause degraded/empty decoding, not the sticky state.

 6. 20%  Missing model in the packaged build
         asar/extraResources path mismatch means the recognizer cannot
         initialize. Would typically surface at init, not as a silent
         "Reconnecting".

 7. 15%  ORT DLL load-order conflict
         Real: Sherpa-first breaks onnxruntime-node with "The operating
         system cannot run %1"; ORT-first works. Current load order is
         ORT-first, so not the active cause today, but fragile.

 8. <5%  Native module / Electron ABI load failure
         Ruled out empirically: modules=150 / napi=10, module loads and
         decodes under Electron 45.2.3.

 9.  0%  Sherpa reconnect loop
         No such code exists in SherpaSTT.

6. RECOMMENDED FIXES (NOT APPLIED)
--------------------------------------------------------------------------------
Priority 1 — Decode path (unblocks transcription)
  - In drainSegments(), call vad.front(false) and always vad.pop() in a
    finally block so the queue advances even on a read failure.
  - Keep decodeSegment's error handling, but surface a typed error upward.

Priority 2 — Error propagation
  - Let SherpaAutoService emit/throw a real error (or return a status object)
    so SherpaSTT can emit 'error'. Today all failures return ''.

Priority 3 — Status state machine
  - Broadcast state='connected' on successful STT start/reconfigure.
  - Reset STT status on session reset (onSessionReset should clear stt).
  - Optionally include a 'starting' state distinct from 'reconnecting'.

Priority 4 — Provider determinism
  - Do not silently self-heal 'none' -> 'natively' when the user explicitly
    selected Sherpa. Log the resolved provider in stt-status.

Priority 5 — Sample-rate flags
  - Only set _micSttRateApplied / _sysSttRateApplied when
    setSampleRate() actually received a positive rate.

Priority 6 — Packaging / ORT
  - Keep ORT-first load order, or pin/align onnxruntime versions between
    onnxruntime-node and sherpa-onnx-node.
  - Verify asarUnpack/extraResources include the Sherpa model dirs.
